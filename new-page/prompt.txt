### Requirements

1. **Standalone document:** Begin with <!DOCTYPE html>. Include charset, viewport, meaningful title and meta description. Use inline CSS, minimal JavaScript, no frameworks or dependencies, and <script src="https://edit.built.at" defer></script> in the head.

2. **Selection and text:** Give meaningful visible content unique, concise, human-readable data-edit labels: sections, cards, headings, paragraphs, labels, images, icons, links, buttons and form fields. Selectable parent components and their content must be independently named. Put editable text on leaf elements; do not wrap the same text in nested editable text containers. A structural parent may contain independently editable children. For a link with an icon, name the link, icon and separate text span independently. Do not add empty text elements. Never use data-label or reserved data-edit values.

3. **Structure:** Use semantic HTML and ordinary CSS classes. Keep reorderable sections as siblings, repeated cards as siblings, and list items as siblings. Give each repeatable item one clear outer element containing all its content, so duplicating or moving it preserves its structure. Use the same structure for equivalent items. Name collections descriptively, such as data-edit="Footer links"; links are ordinary editable elements. Do not use data-section or additional collection attributes. Use IDs only for anchors, labels and accessibility references.

4. **Related elements:** Optional data-edit-group identifies genuinely equivalent elements for shared style editing. Every member still needs a unique data-edit label. Group cards separately from their headings, paragraphs, buttons and icons. Do not group unrelated elements simply because they share a tag or class. Groups share style changes, never individual content.

5. **Design and shared colors:** Follow the brief without unnecessary sections or decoration. Define meaningful reusable CSS variables on :root for shared colors, typography and dimensions. Give independently adjustable colors their own variables, for example --accent, --page-background, --surface and --text. Derive related shades and opacity from their base variable using var() and color-mix(), rather than unrelated hardcoded colors. Use those variables consistently. Keep component styles in classes and allow inline element overrides. Avoid global button, input or SVG styles that could interfere with the editor. Use .button for button-style links and buttons.

6. **Icons:** Prefer real inline Lucide SVGs, unless another icon system is requested. Include actual paths, viewBox and a valid kebab-case data-lucide name; no CDN, Unicode substitutes or placeholder paths. Each icon has its own unique data-edit label. Use stroke="currentColor" for outlines or fill="currentColor" for filled artwork. Give the SVG its own CSS color and independently adjustable width/height, so changing its color does not change adjacent text. Preserve stroke width and alignment. Keep adjacent text in a separately editable span. Equivalent icons may share a data-edit-group. Custom illustrations should not claim a Lucide identity.

7. **Content and accessibility:** Use semantic, accessible, responsive HTML. Make paragraphs individually editable, use real labels for form controls, and give inputs and textareas their own data-edit labels and useful placeholders. Use meaningful image alt text and absolute HTTPS image URLs. Prefer self-contained visuals where appropriate. Preserve native input types and valid nesting.

8. **Editor responsibility:** Do not recreate editor controls, drag handles, selection, local drafts, undo/redo, export or icon replacement. The installed Built.at script handles these. The HTML supplies predictable structure, names, explicit groups and shared CSS variables.
